段階 1 の一致を確かめる基準に関わる TypeScript のテストの調査

2026-11-08。Issue #122。対象は、計画の段階 1 で作る 4 つの基準(会話ログの corpus、fleet CLI の契約、HTTP/WS の契約、安全上の判定の表)が置き換える TypeScript のテストと、その入口のコード。手順は improve-codebase-architecture、語は codebase-design(module、interface、depth、seam、adapter、leverage、locality)と docs/rust-migration/GLOSSARY.md に従う。

調べ方: 段階 1 の基準は計画が決めているので、変更の多いファイルからではなく、基準ごとに今のテストの入口を調べた。subagent 2 つが、transcript の解析のテストと安全上の判定のテストを読み、lead が server/*.contract.test.ts の 15 ファイル(5,391 行)と bin/fleet.test.ts を読んだ。数と file:line は ADR 0122-parity-criteria の「確かめたこと」にある。

Problem: 契約のテストはサーバーを同じプロセスで作り、テスト用のオプションを関数で渡し、テストのプロセスの環境変数を書き換え、サーバーの内部の定数と状態を import するので、別の実装(Rust の core)に向けられない。

Solution: サーバーを「起動の指定(本番が受ける環境変数と、データだけで書けるテスト用のオプション)→ URL」という interface の launcher で別のプロセスとして起動し、テストは URL だけで話す。テスト用のオプションはテスト用のエントリーポイントだけが読む。

  • adapter が 2 つ(TypeScript、Rust)で本物の seam
  • 同じテストで 2 つの実装を比べる
  • 本番の実行ファイルにテスト用の経路がない
  • 環境変数の書き換えが消える

Problem: 同じ判定が、配列の表、個別の assert、子プロセスに env を動かして調べるテストに分かれ、ループバックでない接続元のような black-box では作れない入力の件が、どこにどれだけあるかを一覧できない。

Solution: 判定ごとに持ち主の crate を 1 つ決め、「入力 → 判定」の件を JSON の表にする。各ルートが判定を通しているかは HTTP/WS の契約に残す。

  • Rust の crate ごとの runner に写せる
  • 表と契約の役割が分かれる
  • 件の数が一覧できる

Problem: 起動されたエージェントの指示文が CLI の引数・出力・終了コードに依存しているのに、それを確かめる件が 3 つしかなく、終了コード 4 と 124、wait の replacedBy の追跡、--json の出力に件がない。

Solution: 「argv、環境変数、stub の応答 → 送った要求、標準出力、標準エラー、終了コード」を件にし、runner が選んだ CLI の実行ファイルに当てる。時刻の表示は TZ=UTC、LANG=en_US.UTF-8 に固定する。

  • Rust の CLI に同じ件を当てる
  • 全コマンドに件

5. X-Herdr-Fleet の確認と git の core.fsmonitor=false に、呼べる関数を作る

Speculativein-process

Problem: どちらの決まりも呼べる関数がないので、安全上の判定の表に置けない。

Solution: TypeScript では変えない。ADR 0107-crate-split が、Rust で X-Herdr-Fleet の確認を core のアクセス制御に、git の起動の決まりを child-process に移すと決めている。段階 1 では HTTP/WS の契約と既存のテストで確かめ、段階 3 と 4 の Rust のテストに引き継ぐ。段階 1 は TypeScript のサーバーのコードを変えないので、ここは掘り下げない。

一番の推奨: 1(起動の指定)

候補 1 を最初に決める。理由は 3 つの事実による。4 つの基準のうち、Rust の crate の公開の口を決めるのは候補 1 だけ(core の serve(Config, Seams) と、テスト用のエントリーポイントの置き場所)。HTTP/WS の契約の 13 ファイルの書き換え(4 つの Issue)が、この launcher を待つ。テスト用のオプションの渡し方を誤ると、本番の実行ファイルに push の宛先やアクセス制御を緩める経路ができ、CLAUDE.md の「守ること」に反する。

候補 2〜4 も段階 1 で作る(計画が 4 つの基準のすべてを求めるため)。4 つの基準の形、毎回違う値の扱い、判定の持ち主、ファイルの配置は、ADR 0122-parity-criteria に書いた。人に聞く手順(どの候補を掘り下げるか、grilling)は、決まりのとおり architect への問い(run 42548e4e)と lead の判断に置き換え、その答えを ADR に書いた。
