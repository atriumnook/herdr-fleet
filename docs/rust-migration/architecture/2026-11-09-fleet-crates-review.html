段階 3 の herdr と fleet の crate に移す TypeScript のコードの調査

2026-11-09。Issue #242。対象は、計画の段階 3 で Rust の herdr-fleet-herdr-api、herdr-fleet-herdr、herdr-fleet-child-process、herdr-fleet-orchestrator、herdr-fleet-cli に移すコード: herdr の socket のクライアント(server/herdr/client.ts、404 行)、ペインの状態の購読(server/collector.ts、480 行)、子プロセスの決まり(server/cli-child.ts、server/opencode-cli.ts)、fleet の orchestrator(server/fleet/orchestrator.ts、1,936 行)と server/fleet/ のほかのファイル、bin/fleet.ts(335 行)。手順は improve-codebase-architecture、語は codebase-design(module、interface、depth、seam、adapter、leverage、locality)と docs/rust-migration/GLOSSARY.md に従う。行番号は rust のコミット d7965e3 のもの。

調べ方: 範囲は計画が決めている。2026-10-15 以降のコミットで変更の多いファイル(git log --since=2026-10-15 --name-only --format= -- server/fleet server/herdr server/collector.ts bin/fleet.ts server/cli-child.ts server/opencode-cli.ts の出力をファイルごとに数えた)は、server/fleet/orchestrator.ts(37 回)、events.ts(8)、metrics.ts(7)、adapters.ts(7)、outbox.ts(5)で、orchestrator に変更が集まっている。subagent 3 つが、orchestrator とそのテスト、herdr のクライアントと購読、子プロセス・使用量・モデル一覧・fleet CLI の契約を調べ、lead が要点を読んで確かめた。

Problem: 起動、委ねたターン、thread の landing、coordinator への知らせ、計画が 1 つの class の private の Map を直接読み書きし、委ねたターンの決着(finalize 1420、settleThreadTurn 1478)が、ほかのほとんどの関心の処理を呼ぶ。1 つの関心を直すにも、ほかの関心が触る Map と lock の順序を読む必要がある。テストの describe も関心をまたぐ(「a thread outlives its lead run」の 22 件は、起動し直し、landing、知らせを合わせて試す)。

Solution: Rust では、共有する状態(run、委ねたターン、lock、知らせ、監督の時刻)の型を土台の module が最初にすべて決め、関心ごとの impl を別のファイルに置く。委ねたターンの決着の流れ(finalize)は土台が 1 回だけ書き、各関心の関数を呼ぶ。

  • 関心ごとの作業が別々のファイルで並行できる
  • 状態と lock の順序を読む場所が 1 つになる(locality)
  • テストは公開の口(/api/fleet の操作に当たる method)と FakeRuntime で書ける

Solution: child-process に、起動の種類(使用量の probe、モデル一覧、opencode api、git)ごとに環境変数と作業フォルダーと上限を決めた 1 つの起動の口を置く。呼ぶ側は種類を選ぶだけにする。

  • TypeScript と振る舞いが変わる箇所(上限と SIGKILL を足す)は、決めたうえで ADR に書く

Solution: 段階 3 の土台の Issue が shared/fleet.ts の型を protocol に置き、CLI は、応答の任意の項目が欠けていても読み込みに失敗しないように型を読む。正しいかは fleet CLI の契約(87 件)で確かめる。

一番の推奨: 1. orchestrator の関心ごとの module と、共有する状態の 1 か所

段階 3 の作業を並行できるかは、orchestrator の共有する状態(run、委ねたターン、lock、知らせ)と委ねたターンの決着の流れを最初の Issue が書き終え、あとの Issue が関心ごとのファイルだけを書けるかで決まる。orchestrator は段階 3 のコードの半分を占め、変更も集まっているので、最初に決める。候補 2 と 3 は ADR 0107-crate-split がすでに方向を決めたもので、段階 3 の土台の Issue がその形を作る。候補 4 と 5 は、段階 3 と段階 4 の境目と、crate の間の型の置き場所の問題である。ADR 0242-phase-3-split は、architect に聞いた答えをもとに、1〜5 を Issue の分け方にした。
