Problem: 画面を読む知識が prompt.ts と adapters.ts に分かれ、どちらも seam の向こうの I/O(codex.ts の sqlite と herdr、model-lists.ts の子プロセス)を import している。

Solution: 「エージェントの種類と画面の文字 → カード、答えのキー、画面の判定」を interface にした 1 つの module にし、型 QueuedQuestion もそこへ移す。

  • 画面の corpus がこの interface だけを叩く
  • locality: 画面の癖が 1 か所に集まる
  • I/O の import が 0 になる

Problem: 子プロセスの安全上の規則(最小の環境変数、使用量の probe などの私用の空のフォルダー、タイムアウトと kill)を、cli-child.ts の部品を呼ぶ 5 つのファイルがそれぞれ組み立てている。どの部品を使うかはファイルごとに違う(サイドチャットはプロジェクトのフォルダーで動くので、環境変数の部品だけを使う)。git を core.fsmonitor=false で動かす決まりは files.ts と fleet/thread.ts に重複している。

Solution: 子プロセスの起動を 1 つの module にまとめ、起動の種類(空のフォルダーで動かす probe と Explain、呼ぶ側のフォルダーで動かすサイドチャットと git)ごとに、環境と作業フォルダーとタイムアウトを内側で決める。parseX(output) の関数は純粋なまま、使う側の module に残す。

  • 安全上の判定の表が 1 つの interface を叩く
  • API キーを渡さない規則が 1 か所

使う module が fleet と core の両方にあるので、どちらからも使える場所に置く必要がある。置き場所は ADR 0107-crate-split で決めた(crate herdr-fleet-child-process)。

  • #109 の選択が 1 つの module に閉じる

一番の推奨

候補 2(transcript の解析と場所の特定を分ける)を最初に手がける。結合が一番深く(conversation.ts と codex.ts の 2,680 行が herdr・sqlite・子プロセスと解析を混ぜている)、段階 2 の Rust の実装を会話ログの corpus だけでテストするには、解析が I/O を import しないこの seam が要るため。

crate の分け方としては、候補 1、2、3、4、5、7 を crate の境界にし、候補 6 は core の中の module の分け方にする。決定と理由は ADR docs/rust-migration/adr/0107-crate-split.md にある。
